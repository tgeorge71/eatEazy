# eatEazy

Decision-fatigue reducer for "what's for dinner" — state your constraints once, get 3 meal
options on demand, and turn the pick into a grocery list.

A React Native (Expo) app with a small FastAPI backend that calls Claude to generate suggestions.

## Backend setup

The app talks to a local FastAPI server (`main.py`) that holds the Anthropic API key —
suggestions are never generated by calling Anthropic directly from the app.

```
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
# Add ANTHROPIC_API_KEY to your backend .env file
uvicorn main:app --reload --host 0.0.0.0 --port 8000
```

`GET /health` should return `{"status": "ok"}`. Until `ANTHROPIC_API_KEY` is set, `/suggestions`
returns a clear 503 rather than mock data.

## Frontend setup

Requires [Node.js](https://nodejs.org/) and npm.

```
npm install
npm start
```

Then choose a platform:

```
npm run ios      # iOS simulator (macOS + Xcode)
npm run android   # Android emulator
npm run web       # Browser
```

Or scan the QR code from `npm start` with the [Expo Go](https://expo.dev/client) app on your phone.

The app reads the backend URL from `EXPO_PUBLIC_API_URL` in `.env` . The
default (`http://localhost:8000`) works for the web target and simulators; on a physical device
via Expo Go, point it at your machine's LAN IP instead, since the phone can't resolve `localhost`
as your computer.

## Workout-aware planning

Open **Fitness profile & workouts** from the home screen. Enter your profile in metric
or imperial units, choose balanced maintenance, strength, or endurance, and review the
editable macro percentages. Usual activity includes usual workouts: exercise calories
are not added a second time. Daily targets use Mifflin–St Jeor with activity factors
1.2 / 1.375 / 1.55 / 1.725; these are estimates, not individualized prescriptions.
Automatic targets are limited to adults who are not pregnant or breastfeeding.
Manual calorie and macro overrides are available.

Add multiple planned or completed workouts to each date in the seven-day schedule.
Future workouts must remain planned. Enable workout-sharing consent to send date,
type, duration, and completion status to Claude; without consent, meal planning uses
nutrition targets only. Profile and schedule stay in local app storage. Personal
measurements go to the Python server for calculation, not to Claude.

**Plan tonight** works with existing preferences. **Plan today** and **Plan this week**
require a saved fitness profile and produce breakfast, lunch, dinner, and optionally a
snack. Weekly plans generate one day at a time; retry failed days individually. Each
meal has three choices and up to three rerolls. Nutrition is AI-estimated **per serving**;
ingredients are scaled to household size. Selected totals describe planned food,
not consumed food. Grocery lists include every selected meal type.

### Android and iPhone testing

Start the backend with the command above and run `npm start`. Set
`EXPO_PUBLIC_API_URL=http://YOUR_COMPUTER_LAN_IP:8000` in `.env`, restart Expo, and use
a physical device on the same Wi-Fi. `localhost` on a phone points at the phone.
For local native debug builds, use `npx expo run:ios` with full Xcode, or
`npx expo run:android` with an Android SDK. These commands generate native project
folders. No native health module is needed for the manual prototype. Browser testing
remains available with `npm run web`. Expo Go must support the project’s Expo SDK 51;
use a native debug build if your installed Expo Go is incompatible.

Device acceptance checklist: save/reopen your profile; toggle units; add a completed
workout today and a planned workout tomorrow; toggle consent; plan today and a week;
choose meals and verify totals/groceries; interrupt the backend to check day errors
and retry. Native build and physical-device validation require the relevant SDKs
and devices and must be performed before distributing the app.

### Google Health connection

1. Place the downloaded **Web application** OAuth credential file at
   `client_secret.json` beside `main.py`. This file and `.health/` are ignored by Git.
   Do not put credentials under `src/`, assets, or any `EXPO_PUBLIC_` variable.
2. In Google Cloud, add this exact authorized redirect URI to that OAuth client:
   `http://localhost:8000/google-health/callback`.
3. Enable Google Health API, add yourself as an OAuth test user, and allow the scope
   `https://www.googleapis.com/auth/googlehealth.activity_and_fitness.readonly`.
   Sign in to the Google Health mobile app with that same account first.
4. Install backend dependencies with `pip install -r requirements.txt`, restart the
   backend (use `uvicorn main:app --reload --port 8000 --no-access-log` to keep OAuth
   callback codes out of access logs) and frontend, then sign in to eatEazy. The app asks whether you want to connect Google Health; you can skip this step and connect later from **Account & connections**.
5. Sign in with Google, then choose **Connect Google Health** and **Continue to Google**, allow read-only workout access, and return to eatEazy,
   and choose **Sync workouts**. The app displays completed sessions from the last seven
   days. Enable and save the separate workout-sharing toggle to use them in AI planning.

See [Google's current setup guide](https://developers.google.com/health/setup).
OAuth consent is separate from consent to send workout summaries to Claude. Synced
workouts are held in memory and must be synced again after restarting. The manual
schedule remains available for future workouts. Exercise calorie estimates are never
added to daily nutrition targets.

The backend verifies the linked Health identity before marking a connection successful.
Access/refresh tokens and the Health user ID are encrypted in `.health/connections.sqlite3`.
A private `.health/token.key` is generated automatically; keep it with the database when
backing up. Optionally provide a Fernet key as `GOOGLE_HEALTH_TOKEN_KEY` in the backend
`.env` instead. Never change that key while retaining encrypted connections.

The app holds a separate opaque device credential in native SecureStore or browser
session storage, not Google tokens. Google grants are isolated by that credential;
Google SSO identifies the account, while Health grants remain per device. Connect
separately on each device. Closing a browser tab clears its session credential; disconnect
before closing, or revoke eatEazy from your Google account if you lose access to a session.

**Disconnect & delete connection** revokes Google authorization, deletes the server
Health grant and pending authorization, keeps the eatEazy sign-in session, and clears synced
workouts. If Google cannot process revocation, the app reports an error and retains the
connection so you can retry. Manual profile/schedule data remains available. Google
revocation may affect other connections to the same OAuth application.

For physical-phone OAuth, run the backend behind HTTPS, register its HTTPS
`/google-health/callback` URI, and set both `GOOGLE_HEALTH_REDIRECT_URI` (backend) and
`EXPO_PUBLIC_API_URL` (app) to the corresponding addresses. The default localhost
callback is for testing in a browser on your computer. Use HTTPS when transporting real
health data outside loopback; do not publicly deploy this personal prototype without
adding production operational controls. The callback opens in the
system browser; no embedded Google sign-in WebView is used.

Optional backend settings:

```dotenv
GOOGLE_HEALTH_CLIENT_SECRET_FILE=/absolute/path/to/client_secret.json
GOOGLE_HEALTH_REDIRECT_URI=http://localhost:8000/google-health/callback
```

An existing native debug build must be rebuilt after adding SecureStore. Native build
and live Google-account validation require your SDKs/devices and configured credential
file; automated tests mock Google and never authorize or access your real health data.

### Verification

```bash
npm run typecheck
node tests/frontend.cjs
node tests/google_frontend.cjs
.venv/bin/python -m unittest discover -s tests -v
```

The tests use mocked AI responses and do not spend API credits. They cover target
math, allocations, eligibility, manual overrides, malformed AI nutrition, consent,
legacy dinner requests, date rollover, unit conversion, selected totals, and groceries.
Google tests cover PKCE, single-use state, cancellation, expired authorization, linked
identity validation, encrypted storage, device isolation, token refresh/revocation,
workout pagination, civil dates, and native/browser connection credential storage.

### Google sign-in

The app starts with **Sign in with Google**, using a backend OpenID Connect
code flow with PKCE, single-use state, nonce checks, and Google's ID-token verifier.
Login requests only `openid email profile`. **Sign up with email** and **Use phone number**
are placeholders for now: they collect input but show "coming soon"; Google is the only working sign-in. Google Health permission is requested
separately after login; **Continue to meal planning** skips the optional connection.
The same Google account must be used for both steps. Workout sharing with Claude
still requires its separate saved consent.

Use the existing Web OAuth client and authorized callback
`http://localhost:8000/google-health/callback`; no second callback is required.
In Google Cloud OAuth Data Access, include `openid`,
`https://www.googleapis.com/auth/userinfo.email`,
`https://www.googleapis.com/auth/userinfo.profile`, and the existing read-only
Google Health activity scope. Add your account as a test user when applicable.
Restart the Python backend and run `npm run web` to test locally.
Google authorization completes in a separate browser tab/window; return to the app
and it detects completion automatically. On a phone use the configured HTTPS backend
callback described above.

Sessions expire after seven days. **Sign out & disconnect Google Health** revokes
Health access and deletes the server session. If revocation fails, retry sign-out.
**Disconnect & delete connection** removes Health access while keeping you signed in.
Preferences and fitness settings are stored locally per Google account, with no
cross-device data sync. Earlier unscoped prototype settings are left untouched and
are not automatically assigned to a Google account; enter your settings again.
Existing Health-only prototype connections must be disconnected/reset before login.
Automated SSO tests mock Google; live consent and phone testing are still required.
